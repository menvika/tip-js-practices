## 1. Цель работы

Цель работы — подключить браузерное приложение к учебному HTTP API и организовать предсказуемую обработку асинхронных операций. В ходе работы реализованы общий HTTP-клиент для методов `GET`, `POST`, `PATCH` и `DELETE`, предметный API задач, проверка формы, безопасное построение карточек и контроллер состояний интерфейса. Приложение получает данные с сервера, создаёт и редактирует задачи, меняет их статус, удаляет записи и повторно загружает список после изменения. Для предотвращения гонки запросов используются `AbortController` и проверка актуальности результата.

## 3. Реализация

### 3.1. HTTP-клиент

В `src/api-client.js` реализован общий клиент на основе `fetch`. Он поддерживает методы `GET`, `POST`, `PATCH` и `DELETE`, кодирование query-параметров, заголовок `Accept: application/json` и передачу JSON-тела с заголовком `Content-Type: application/json`. Запросы `GET` с телом и неподдерживаемые HTTP-методы отклоняются до обращения к серверу. Для ответа `204 No Content` клиент возвращает `null`, не вызывая `response.json()`. HTTP-ошибки преобразуются в `ApiError` с сохранением статуса, кода, деталей и URL. Также различаются сетевые ошибки, ошибки формата ответа, тайм-аут и внешняя отмена запроса.

### 3.2. Доменный API

В `src/task-api.js` реализованы функции `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`, `createTask`, `updateTask`, `setTaskCompleted`, `deleteTask` и `resetDemoData`. Модуль проверяет идентификаторы, параметры фильтрации, структуру задач и категорий, а также конверты ответов сервера. Начальная загрузка списка задач и категорий выполняется параллельно через `Promise.all`. Предметный API не обращается к DOM и использует общий HTTP-клиент для всех запросов.

### 3.3. Состояния интерфейса

Контроллер отображает состояния `loading`, `ready`, `empty` и `error`. Во время загрузки устанавливается `aria-busy="true"`; после успешного ответа показываются карточки или отдельное состояние пустой выборки. При ошибке выводится сообщение и становится доступна кнопка повторной загрузки. При повторной загрузке, если категории ещё не были получены, снова запрашиваются и задачи, и категории. Изменяющие операции блокируют соответствующие элементы интерфейса и снимают блокировку в `finally`.

### 3.4. Изменение данных

Форма проверяется до отправки запроса: название обрезается по краям и должно содержать от 1 до 100 символов, приоритет должен быть одним из `low`, `medium`, `high`, а категория должна существовать в загруженном справочнике. Реализованы создание задачи через `POST`, редактирование через `PATCH`, изменение `completed` через `PATCH`, удаление через `DELETE` и восстановление учебного набора. После успешной мутации список повторно запрашивается с текущими фильтрами, поэтому сервер остаётся источником истины. Пользовательские данные выводятся через `textContent`.

### 3.5. Защита от устаревшего ответа

Перед началом новой загрузки контроллер отменяет предыдущий запрос с помощью `AbortController`. Каждому запросу присваивается порядковый номер. Результат обновляет интерфейс только в том случае, если номер совпадает с последним актуальным запросом. Это предотвращает ситуацию, когда медленный ответ на предыдущий фильтр заменяет результаты более нового запроса. Ожидаемая отмена не отображается как ошибка для пользователя.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?** Потому что 404 — это полученный HTTP-ответ. Promise отклоняется при сетевой ошибке или отмене, поэтому статус необходимо проверять через `response.ok`.
2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?** У ответа `204 No Content` нет тела, и попытка разобрать пустое тело как JSON завершится ошибкой. Клиент должен вернуть `null`.
3. **Чем состояние `empty` отличается от `error`?** `empty` означает, что запрос выполнен успешно, но результатов нет. `error` означает, что запрос не удалось выполнить или обработать корректно.
4. **Зачем отменять предыдущий запрос при смене фильтров?** Чтобы не тратить ресурсы на уже неактуальную загрузку и снизить риск отображения результатов старого фильтра.
5. **Почему после мутации список повторно запрашивается у API?** Сервер является источником истины. Повторный `GET` возвращает подтверждённое состояние с учётом текущих фильтров, а не только локально изменённую копию.

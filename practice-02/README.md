## 4. Модель данных и функции

**Поля задачи:
{
  id: number,          - положительное целое число, уникальное в пределах набора
  title: string,       - непустая строка, до 100 символов после trim
  completed: boolean,  - true или false
  priority: string     - "low", "medium" (по умолчанию) или "high"
}

**Правила валидации:
Валидация выполняется в `createTask`. Остальные операции переиспользуют её правила: `addTask` — через прямой вызов `createTask, renameTask`— через `createTask` на копии задачи с новым названием, чтобы не дублировать проверки.

**Назначение файлов:
- `src/data.js` — данные: `demoTasks, variantNumber, variantTasks`. Только константы, никакой логики.
- `src/task-service.js` — прикладная логика: девять функций, валидация, создание новых массивов. Не мутирует входные данные.
- `src/main.js` — сценарий: только вызовы функций и вывод в консоль. Заменяет текущее состояние результатом `result.tasks` при успехе, оставляет прежним при ошибке.
- `checks.js` — 35 проверок на `node:assert/strict`. Не входит в прикладной код.

## 9. Вывод

По сравнению с ПР1, где каждая программа работала с отдельными переменными и выводом в консоль, в ПР2 появилась единая модель задачи и модуль функций с предсказуемым контрактом. Все девять функций возвращают либо объект-результат `{ ok: true, tasks: [...] }` / `{ ok: false, error: "..." }`, либо новое значение, не изменяя входные данные. Это оказалось важным для сценария: возвращаемые значения используются для замены текущего состояния — при `result.ok === true` массив `currentTasks` заменяется на `result.tasks`, при `false` остаётся прежним. Так повторное добавление id = 80 было отклонено без повреждения набора.

Неизменность данных проверена двумя способами: в конце `main.js` выводится `demoTasks.map(t => t.id)` и `variantTasks.map(t => t.id)` — оба массива сохранили исходный состав и порядок; кроме того, в `checks.js` отдельный сценарий (№ 33) явно проверяет, что ни одна из девяти операций не мутирует входные объекты.

Основная ошибка, которую пришлось исправить: в первых версиях функций оставались обращения к несуществующей переменной `completed` вне контекста колбэка, а также мутирующие операции (`push`, `splice`, присваивание полю объекта). Первое давало `ReferenceError: completed is not defined` почти во всех проверках, второе нарушало контракт «входные данные не изменяются». Обе причины устранены: `createTask` вызывается только с валидными аргументами, а изменения выполняются через `filter`, `map` и спред-копии `{ ...task, поле: значение }`.

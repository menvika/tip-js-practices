## Эксперименты с формой и хранилищем

| № | До запуска: прогноз | После запуска: результат | Объяснение |
|---:|---|---|---|
| 1. Пустое обязательное название | Браузер должен заблокировать отправку до события `submit`. | Ошибка незаполненного поля | Обработчик `submit` не вызывается |
| 2. Название из пробелов | Нативный `required` может пропустить строку из пробелов, прикладная проверка должна её отклонить. | `Название не должно состоять только из пробелов.` | выводится ошибка и сохранения не происходит. |
| 3. Корректные значения | `FormData` должен вернуть значения полей в виде строк; после успешной проверки данные будут записаны. |`submit.defaultPrevented: true typeof FormData title: string typeof localStorage value: string {   "value": {     "title": "lldkdkddk",     "priority": "low"   },   "serialized": "{\"title\":\"lldkdkddk\",\"priority\":\"low\"}" }` | В журнале отображаются `typeof FormData title`, `event.defaultPrevented`, нормализованное значение и сериализованная JSON-строка. |
| 4. Чтение сохранённого значения | `localStorage.getItem` вернёт строку, а `JSON.parse` восстановит объект. | `JSON прочитан успешно:{  "raw": "{\"title\":\"lldkdkddk\",\"priority\":\"low\"}",  "parsed": {    "title": "lldkdkddk",    "priority": "low"  }}` | отображаются в журнале отдельно |
| 5. Повреждённый JSON | `JSON.parse` выбросит исключение. | `В учебный ключ записана строка с повреждённым JSON.` | При чтении строки исключение перехватывается через, страница продолжает работать и показывает сообщение об ошибке. |

## Организация кода

Модули разделены по ответственности. `task-service.js` содержит правила модели задач и не обращается к DOM или хранилищу. `form-validation.js` проверяет входной черновик и возвращает структурированный результат, не показывая сообщения самостоятельно. `task-view.js` отвечает только за создание и отображение элементов интерфейса. `task-storage.js` работает с JSON и обрабатывает исключения. `main.js` координирует события и текущее состояние.

Функции хранилища получают объект `storage` аргументом. Благодаря этому их можно проверять на объекте-имитации, не используя реальный `localStorage`. Данные из JSON проверяются до использования, потому что успешный `JSON.parse` подтверждает только корректность синтаксиса, но не правильность структуры и значений.

## Проверка восстановления и ошибок

| Случай | Ожидание | Фактический результат | Итог |
|---|---|---|---|
| Записи нет | Используется независимая копия исходного набора | При `getItem` → `null` возвращается копия `initialTasks`, `source: "initial"`; изменения не затрагивают исходный массив | Успех |
| Корректная запись | Данные восстанавливаются после перезагрузки | После add/update/toggle/delete в localStorage лежит `{ version: 1, tasks: [...] }`; при перезагрузке `source: "storage"`, состав совпадает | Успех |
| Повреждённый JSON | Приложение запускается с исходным набором и предупреждением | При записи `{broken-json` и перезагрузке — исходный набор и предупреждение о повреждённых данных, приложение работает | Успех |
| Неверная версия или схема | Исходный набор и предупреждение | При `version: 2` или неверной схеме задач возвращается fallback с ошибкой, список не применяется частично | Успех |
| Сброс | Удаляется только ключ текущего набора | `removeSavedTasks` удаляет ровно `tip-js-practice-04:demo`; другие ключи origin не затронуты, `clear()` не используется | Успех |
| Общий и индивидуальный наборы | Изменения не смешиваются | demo и variant используют разные ключи (`:demo` / `:variant`); изменения в одном не появляются в другом | Успех |

## Отладка `handleFormSubmit`

Точка останова установлена в `main.js` в функции `handleFormSubmit` — на строке после формирования `draft` и на строке после вызова `validateTaskDraft`. Сценарий: добавление задачи `id = 20`, затем повторная попытка с `id = 4`.

| Момент | Что наблюдалось |
|---|---|
| Сырой `draft` (создание, корректный ввод) | `{ id: "20", title: "  Изучить localStorage  ", priority: "high" }` — все значения строки, `id` не число, в `title` краевые пробелы |
| Результат `validateTaskDraft` | `{ ok: true, value: { id: 20, title: "Изучить localStorage", priority: "high" } }` — `id` приведён к числу, `title` нормализован через `trim` |
| Результат сервисной операции (`addTask`) | `{ ok: true, tasks: [ ... , { id: 20, title: "Изучить localStorage", completed: false, priority: "high" } ] }` — новый массив, исходный не изменён |
| Строка JSON для `saveTasks` | `{"version":1,"tasks":[{"id":1,...},{"id":4,...},{"id":7,...},{"id":10,...},{"id":20,"title":"Изучить localStorage","completed":false,"priority":"high"}]}` |
| Сырой `draft` (повторный `id = 4`) | `{ id: "4", title: "Новая задача", priority: "medium" }` |
| Результат `validateTaskDraft` (повторный id) | `{ ok: false, errors: { id: "Задача с таким идентификатором уже существует" } }` |
| Сервисная операция | Не вызывалась: после `!validation.ok` выполняется `return` |
| Запись JSON | Не выполнялась: `persistTasks()` не вызван, массив в памяти не изменён |

Дополнительно проверено редактирование: при `editingId = 4` поле `id` заблокировано, `formData.get("id") === null`, но `validateTaskDraft` берёт `editingId`, возвращает `value.id === 4`, а `updateTask` сохраняет `completed` текущей задачи без сброса.

## Положение фокуса при редактировании

- **Начало редактирования:** после `setFormMode(id)` фокус устанавливается в поле названия (`titleInput.focus()`), поле `id` заблокировано, заголовок «Редактирование задачи», кнопка отмены видима.
- **Отмена редактирования:** `setFormMode(null)` очищает форму и ошибки, включает поле `id` и переводит фокус в поле `id` (`idInput.focus()`); заголовок «Добавление задачи», кнопка отмены скрыта.
- **После успешного сохранения:** форма возвращается в режим создания, фокус снова в поле `id`.

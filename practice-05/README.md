## Эксперимент с очередями выполнения

До запуска `npm run example:order` записать прогноз порядка меток. После запуска внести фактический порядок и объяснить каждую позицию.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A → B → C → D → E → F | Сначала выполняется синхронный код. Затем выполняются микрозадачи: обработчик Promise и продолжение после await. Последним выполняется таймер. |
| Фактический результат | ```A: синхронный код B: начало async-функции C: конец синхронного кода D: обработчик Promise E: продолжение после await F: задача таймера``` | соотвествуют ожиданию |

- синхронный код: сообщения A, B и C выводятся во время основного выполнения программы. Функция demonstrateAwait() начинает выполняться сразу, но при встрече с await null приостанавливается.
- очередь микрозадач: обработчик Promise.resolve().then(...) выводит сообщение D. Продолжение функции после await выводит сообщение E. Обработчик D регистрируется раньше продолжения E, поэтому D выводится первым.
- таймер с задержкой 0. Сообщение F выводится последним. Нулевая задержка не означает немедленного выполнения: колбэк таймера ожидает завершения синхронного кода и обработки микрозадач.
- удаление обработчика Promise. Если удалить обработчик, выводящий D, сообщение D исчезнет, но продолжение после await сохранится. Порядок оставшихся сообщений будет A → B → C → E → F.

## Организация кода

Кратко описать ответственность файлов:

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Запускает HTTP-сервер, обрабатывает запросы к API и возвращает ответы с данными или ошибками. |
| `src/api-client.js` | Создаёт клиент для работы с API, выполняет HTTP-запросы, обрабатывает сетевые и HTTP-ошибки, проверяет формат ответов. |
| `src/task-api.js` | Содержит функции для получения и изменения задач через API-клиент. |
| `src/variant.js` | Хранит данные и настройки варианта задания, которые используются при работе приложения. |
| `src/main.js` | Точка входа приложения. Связывает основные модули и запускает выполнение программы. |

`fetchFn` передаётся в `createApiClient`, чтобы клиент мог использовать переданную функцию для выполнения HTTP-запросов. Это делает код гибче: можно использовать стандартный `fetch` или передать тестовую функцию. Благодаря этому проще проверять работу клиента без настоящих запросов к серверу.

Сетевые ошибки возникают, когда запрос не удалось выполнить, например из-за отсутствия соединения. HTTP-ошибки появляются, когда сервер ответил, но вернул неуспешный статус, например `404 Not Found` или `500 Internal Server Error`. Раздельная обработка помогает понять причину проблемы и правильно сообщить о ней.

Успешный разбор JSON означает только то, что ответ имеет правильный синтаксис. При этом данные могут отсутствовать или иметь неправильную структуру. Проверка контракта позволяет убедиться, что ответ содержит необходимые поля и значения ожидаемого типа. Это помогает избежать ошибок при дальнейшей обработке данных.

**Правила проверки данных**

- задача: проверяются обязательные поля, типы данных и допустимые значения. ID должен быть корректным положительным целым числом, `title` — строкой, `completed` — логическим значением, `priority` — одним из разрешённых приоритетов.
- категория: проверяются структура объекта, обязательные поля, корректность ID и тип названия категории.
- уникальность ID: идентификаторы задач внутри списка и идентификаторы категорий внутри списка не должны повторяться.
- поле `meta.total`: должно быть неотрицательным целым числом и соответствовать количеству элементов в возвращённом массиве.
- фильтры: проверяются допустимость названий фильтров и типов значений. Неизвестные фильтры и некорректные значения приводят к `TypeError` до выполнения запроса.
- обработка ошибок: ошибки HTTP, сетевые ошибки, некорректные ответы и отмена запроса обрабатываются раздельно.
- начальная загрузка: `loadInitialData(...)` параллельно загружает задачи и категории. Если один из запросов завершается ошибкой, она передаётся вызывающему коду.

## Последовательная и параллельная загрузка

Для сравнения производительности были рассмотрены два способа получения задач и категорий через API с использованием маршрута `/debug/delay`. Каждый сценарий необходимо выполнить минимум три раза с одинаковыми задержками, чтобы сравнение было корректным.

```
viktoriamensikova@MacBook-Pro-Viktoria practice-05 % node src/compare-loading.js
Последовательная загрузка:

Параллельная загрузка:
Запуск 1: 1005.0 мс
Запуск 2: 1005.5 мс
Запуск 3: 1005.0 мс
```

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 2013.1 | 2008.8 | 2008.8 | Второй запрос начинается после завершения первого, поэтому общее время складывается из времени обоих запросов. |
| `Promise.all` | 1004.5 | 1002.6 | 1005.4 | Оба запроса запускаются параллельно, поэтому общее время близко ко времени одного запроса. |

Результаты эксперимента показали, что последовательная загрузка занимает примерно 2 секунды, а параллельная — около 1 секунды. Использование `Promise.all` позволяет сократить общее время ожидания примерно в два раза при одинаковой задержке запросов.

При последовательной загрузке выполнение второго запроса начинается только после завершения первого (задержки двух запросов суммируются). При использовании `Promise.all` оба независимых запроса запускаются практически одновременно. В результате общее время ожидания обычно меньше, поскольку приложение ожидает завершения обоих запросов параллельно, а не последовательно.
Фактическое время зависит от задержек API, нагрузки на сервер, сети и компьютера.
